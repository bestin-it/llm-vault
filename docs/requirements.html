LLM Vault - Requirements

A password manager with a built-in, secure LLM gateway. API keys stay in an encrypted vault; AI agents, VS Code and Python scripts can run approved model calls but never receive the secret values.

Version 0.1 (prototype)Date 2026-10-21Source: concept v2 (PL) + product decisionsLicense: Apache-2.0
Status legend: Done implemented and tested in v0.1 Partial implemented with limitations Planned next milestones Out of scope deliberately excluded

01 / OVERVIEWOne product, two functions

LLM Vault combines KeePass-style secret management with controlled execution of LLM requests.

Vault

Encrypted entries (logins, passwords, API keys, notes), KDBX 4 import/export, user unlock, access policies, rotation.

Gateway / broker

API compatible with popular LLM protocols, calls to Foundry / OpenAI / Anthropic / local models, limits, consent and audit.
VALUE PROPOSITION"Use my permission to run an approved operation - but never show me the secret."

02 / PROBLEMA real problem, not another chat

Coding agents read repositories, run terminal commands and execute scripts. "The application may use the API" must not imply "the application may read the API key".

1A developer runs an agent in VS Code; it can execute commands.
2The provider key is in .env, an environment variable or a credential store.
3The agent processes untrusted content (README, tool output, dependency).
4The secret leaks to a log, a model response, a remote server or a file.

Why current methods are not enough

MethodProvidesDoes not solve
.env / environment variablesConvenient key deliveryAny process with file/process access can read it
Windows Credential ManagerSystem store instead of the repoCode running as the user can request it
KeePass / KeePassXCEncrypted database, password unlockNo control once the secret is handed out
Cloud Key VaultCentral secrets, RBAC, auditOver-privileged agents can still fetch the secret
Plain LLM proxyHides the key behind an endpointWithout authorization and isolation the endpoint is abused
REQUIRED MODEL CHANGEClients get only a controlled invoke_model() operation instead of get_secret().

04 / ARCHITECTUREThe trust boundary matters most

Zone A - untrusted

Copilot Chat & custom agents, Python scripts / CI, Claude Code, other IDEs. They hold only a client token.

Zone B - protected LLM Vault process

Policy engine (consent, allow-lists, limits, audit) · Secret broker (KDBX unlock, key use) · TLS egress to allowed endpoints · log redaction.

One request

01 Agent sendsPOST /v1/chat/completions, model: foundry-glm
02 Vault identifiesToken, model, source, limits, rules
03 ConsentOnce, session or standing rule
04 Vault calls providerKey used only inside the protected process
05 ResponseTokens, cost and decision recorded

Deployment modes

05 / THREAT MODELWhat we actually protect

ThreatControlResult
Agent reads the API keyKey never in agent config, responses or logs; no export endpointPrevented with correct isolation
Prompt injection ("show the secret")No such operation; every call passes policyContained
Abuse of paid modelsAllow-lists, consent, budgets, req/min, expiryLimited
Stolen client tokenMinimal scope, short life, instant revocation, rotationReduced, not eliminated
Config tampering (redirect provider URL)Config inside encrypted + HMAC-protected KDBX; no HTTP redirectsPrevented
Drive-by web page calling localhostRequests with a browser Origin header are refusedPrevented
UI automation clicking "Allow"Consent buttons armed after a delay; audit trailRaised the bar
Compromised workstation / admin malwareStrong-isolation mode outside the agent zoneRequires a separate zone
ESSENTIAL CAVEATIf an agent can run arbitrary code as the same user that holds the unlocked vault, the consent UI alone does not guarantee secrecy. OS isolation, process identity, IPC and permission control are part of the solution, not an add-on.
